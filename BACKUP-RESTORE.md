## The export (B2)

`exportDatabase(conn, sink, { pageSize })` runs inside one **read-only** snapshot (`SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`, then `START TRANSACTION READ ONLY, WITH CONSISTENT SNAPSHOT`; the caller's isolation level is left alone, a write meanwhile is refused with 1792) and reads every exported table in **keyset pages** in primary-key order. The whole export is one snapshot on ONE connection, which the dump script (a Custom cron job, I8 (B)) holds from start to finish and **never slices** (a second call would be another snapshot); for that time the session's `wait_timeout` is 300 (Hostinger's server closes an idle connection after 20 s) and the caller's value is put back, also after a failure. Output, through the sink:

- `manifest.json`: format `jewelvault-export-1`, server version, **the migration files the database was built with** (version, name, checksum), per table the columns, the primary key, the row count and the **sha256 of its data file**; `excluded`, `omitted` and `filtered` say what was left out and why; **`filter_cutoffs`** (RV3a-F2) gives, for each table in `filtered`, the instant its rule came to (`{ "sys_idempotency": "2026-07-22 04:12:55.123456" }`, UTC, DATETIME(6) text): the rows kept are those created at or after it, worked out once for the export; the number of live photos; whether the source had triggers. **No table definitions, views or triggers**: `SHOW CREATE TABLE` leaves triggers out, so the migration files in the repository are the schema (B4).
- `data/<table>.ndjson`: one JSON object per row. **Every value is text** (DECIMAL and dates exactly as the server prints them, binary columns as hex, NULL as null), so nothing depends on how the connection was configured. Generated columns are left out (the server computes them).
- Left out: the photo `bytes` (they travel through the photo copy); the tables `sessions` (everyone signs in again) and `sys_login_attempts` (counters, rebuilt by use); `schema_migrations` (replaced by the list in the manifest); the `sys_idempotency` rows older than 90 days (expired, L6), counted from the cutoff in the manifest.

Rules learned while writing it:

- A UUID primary key sorts in the type's own order, **not as text**. In the SELECT list a column that is cast to text and given its own name hides the real column in `ORDER BY id`, so the pages overlapped and skipped rows with random (v4) UUIDs. The export qualifies every key as `src.<column>`. A test with 2-row pages and one with 30,000 random-UUID bills guard it. **Any keyset paging in the API (C4 polling, `(updated_at, id)`) must compare ids as the UUID type, never as text, and must not alias a column to its own name.**
- `copyPhotosOnce(conn, store)` uploads each live photo that has no `sys_photo_copies` row once (oldest first), after checking its bytes against the recorded sha256 and size; then asks the store for the object's size (`head`, a `stat` on the folder) and **only when it equals the photo's size** records `(photo_id, kind, sha256, size)`. A failed write, a missing file or a wrong size records nothing and does not stop the others; the next run retries. A removed photo keeps its copy row (no foreign key). The API's tick calls it with `{ limit }` and a deadline of about 25 s per slice.

## The backup folder and the encrypted file (B2, draft 5.2)

`JV_BACKUP_DIR` is one absolute path with the same value for the app and for cron; `resolveBackupDir(value)` refuses an empty value, a relative path, a `~`, a `..` and the root. **By default `/home/<user>/jv-backup`: a folder of its own in the home folder and OUTSIDE `domains/`** (spec 5.2.2): connecting a domain renames the site's folder in `domains/` and turns the temporary address off, so an absolute path with the old name goes stale (the proof's folder answered ENOENT after the staging domain was connected; nothing was lost). Connect the final domain first, then make the folder. Every hourly run of the dump and the start-up check test that the folder exists and is writable (`probeBackupDir`: a file is really created and removed in it and in each sub-folder that exists, a mode alone does not tell); the folder itself is never made by the code, so a stale path cannot grow a new tree. Layout: `daily/<yyyy-mm-dd>.enc`, `monthly/<yyyy-mm>.enc` (the first run of a month also puts the file there, as a **hard link**: no second copy on disk, and pruning one name leaves the other) and `photos/<photo id>-<kind>`. The business date is the Asia/Kolkata date (`businessDate(ms)`).

**`writeDailyExport({ dir, date, runId, publicKey, exportFn, record, recorded })`** is the whole nightly write:

1. creates the three sub-folders and removes every `*.partial` file older than one hour (`sweepPartials`);
2. **retry rule, step 1:** if `recorded` (`{ name, sha256, size }` from `backup_runs.detail` of an earlier attempt of the same night) names a final file that exists with that sha256 and size, nothing is dumped again and the answer is `already_done` (the earlier attempt only lacked its `ok` row);
3. otherwise the dump goes through `exportFn(sink)` (`exportDatabase(conn, sink)`) into `daily/<date>-<run id>.enc.partial` **inside the snapshot**: container frames → gzip → AES-256-GCM → sha256 and size counted → written, flushed to disk (`fsync`) and closed. There is no separate spool;
4. **`record({ name, sha256, size, run_id })` is called before the file is linked**; the API puts it in `backup_runs.detail`. If the process dies between the link and the `ok` row, step 2 repairs it on the next hourly try;
5. the partial is linked into place with `link()`, which never overwrites. If `daily/<date>.enc` already exists and is not the recorded file, it is left alone, the answer carries the alerts `export_name_taken` (and `export_record_mismatch` when a record was given and did not match) and this run's file is `daily/<date>-<run id>.enc`; if the plain name appears between the check and the link, the same happens and `record` is called a second time with the new name;
6. the monthly link is made when `monthly/<yyyy-mm>.enc` does not exist; the partial is removed. A failed dump or a failed `record` leaves no final file and no partial.

The encrypted file (`export-file.mjs`): `"JVE1" | u16 wrapped-key length | RSA-OAEP(SHA-256) wrapped 32-byte key | 12-byte iv | AES-256-GCM ciphertext | 16-byte tag`, the header being the GCM additional data. After gunzip: `"JVC1"` and frames (begin file, data of at most 256 KiB, end file, end of export; a stream without the end frame is truncated). `BACKUP_PUBLIC_KEY` is a PEM, the base64 of a PEM (one line, as the design asks) or base64 DER (`loadPublicKey`). `unpackExport(encPath, privateKey, outDir)` writes `manifest.json` and `data/*.ndjson` (the layout `directoryStore(outDir).source` reads) and throws on a wrong key, any changed byte, a cut file, trailing bytes or a path that leaves the folder. GCM vouches for the data only at the end, so after a throw the folder must be thrown away. The private key is held by Harsh and by the owner and is never on the server (O40). Photos are copied **as they are, not encrypted** (O11): `directoryPhotos(dir/photos)` writes `<id>-<kind>.<random>.partial`, `fsync`, then `link()`; the same bytes again are accepted, other bytes under the same name are refused (an alert, never an overwrite).

**Pruning has guard rails, because there is no lock to lean on** (`prune(dir, { goodWriteTonight, lastRecordedFiles, dryRunDone })`): only exact name patterns in `daily/` and `monthly/` are touched (a folder, a symbolic link, `photos/`, a `.partial`, `README.txt` or `2026-09-01.enc.bak` never are); the **newest 30 `daily/` and 13 `monthly/` files are always kept whatever their age** ("newest" is the date in the name, then the file time; a retried night can leave two files for one date and 30 counts files); nothing is deleted unless tonight's export was written and its `ok` row is in (after 40 failed nights nothing goes); it refuses a folder with fewer files than the last recorded count; and the first real prune is preceded by a **logged dry run** (`{ action: 'dry_run', candidates }`: the caller stores `detail.prune_dry_run`, and `readPruneState(conn)` tells the next night it may delete). Read `readPruneState` before tonight's row is written.

**The rows** (`recordBackupRun(conn, { kind, ok, bytes, detail })`; `ok` only for a complete phase, D17): `detail.folder = { files, bytes, free_bytes }` (`folderStats(dir)`: final files in the three sub-folders, their size, `statfs`), `detail.pruned` = files this run removed on purpose, `detail.prune_dry_run`, and for the dump `detail.export = { name, sha256, size }`. The dashboard goes **red when the file count falls by more than was pruned** between two good runs (see below).

## The restore (B4)

`restoreDatabase(conn, source, photos, { migrationsDir, triggers, skipInvariants })`, in the order of B4:

0. refuses a database that has any table or view ("not empty"), an export of another format, a data file whose sha256 differs from the manifest, and migration files other than the ones the export was made with: **all before anything is created**;
1. applies the migration files (no seeds, no trigger files) through the same runner, so `schema_migrations` agrees with the repository;
2. loads the data in **foreign-key order** (derived from the keys the migrations made; the keys stay ON; `bills.reissue_of` is loaded in waves, the replaced bill first);
3. inserts each live `design_photos` row **together with its bytes** from the photo copy (size and sha256 checked first). A photo that is missing or does not match is **inserted as a tombstone** (`removed_at` = the restore time), listed in the report as `missing`, `size` or `sha256`, and makes the report not ok: the owner decides about each one;
4. restores tombstones as they are;
5. applies the trigger files last (when the source had them: the append-only triggers of `audit_log` and the audit triggers `0910`), so that loading writes no audit rows;
6. runs `ANALYZE TABLE`, checks the keys, **exports the restored database again and compares every table's content hash with the manifest** (so the row counts too; a table the export kept only in part is read again under the export's own cutoff from `filter_cutoffs`, not under "now minus 90 days" at the restore, which dropped a row that had been 3 seconds inside the window and called a correct restore a failure, RV3a-F2; an export from before the cutoff was written down has none: the restored table is read again whole, which is exact because a restore loads exactly the rows of the export, and the report's `notes` and the printed report say so), checks every restored photo against its sha256 inside the database, and runs the nightly check on the copy.

It works as the restricted user of A3 (the ten ticked boxes) and a test proves it. A failed restore leaves a partly filled database: drop it and start again. A real restore needs a **new empty database** (the app's user has no Drop) and the tool opens its connections through `scripts/pacing.mjs` (at most 10 new connections in any 1.2 seconds, S11; the import CLI does the same). Measured locally: 63,000 rows (30,000 bills) export in about 1 second and restore plus full verification in about 5 seconds; the drill's budget is 2 hours.

## The dashboard line (I12)

`readHealth(conn)` returns the level (`red`, `amber`, `green`), the reasons in dashboard order and the figures: the last check (any result) and whether it said Problem, the last `backup_runs` row with `ok = 1` for `db_dump` and for `photo_copy` (a `restore_drill` row is not a backup), the folder, the owner's download, Harsh's pull, the database size, and what the user may do (from `SHOW GRANTS`).

- Reasons in order: `check_problem`, `check_stale`, `check_never`, `dump_stale`, `dump_never`, `photo_copy_stale`, `photo_copy_never`, `backup_files_fell`, `backup_folder_unusable`, `backup_photos_damaged`, `backup_clock_ahead`, `db_size`, `download_red`, `download_amber`, `pulled_amber`, `backup_photos_repaired`, `delete_or_drop_right`. Red: the first eleven and `download_red`. Amber: nothing red but one of the last four.
- **Download everything (B3, O53)**: whole Asia/Kolkata calendar days from `settings.last_download.at`, or with none from the oldest `check_runs` row (the first night). **Amber at 28 days or more, red above 35**; `download = { state, from, reference_date, age_days }`. Tests: absent, 27, 28, 35, 36 and 60 days, the Kolkata date boundary (18:29 UTC is still the day before), a new download clears it.
- **Harsh's weekly pull (O54)**: from `settings.last_pulled.at`, or with none from the first good export; **amber above 10 days**; `pull = { state, from, reference_date, age_days }`. The row is written by the admin door (`recordPull` in `housekeeping.mjs`), never by the generic settings edit.
- **The folder (B2)**: `folder = { files, bytes, free_bytes, previous_files, recorded_at, fell, fell_at }` from `backup_runs.detail.folder` of the good `db_dump` and `photo_copy` runs. `fell` is true when, between two consecutive good runs in the **last 7 days**, the file count dropped by more than the later run's `detail.pruned`. Seven days (my choice, not the spec's) because a fall seen only until the next run would be gone before anyone looked.
- **A good run dated in the future (RV3a-F4)**: the dump stamps `ran_at` from the clock of the cron host. The age of the last good export and of the last good photo copy is taken from the newest `ok` = 1 row whose `ran_at` is **not after "now" plus 5 minutes** (`CLOCK_SKEW_MINUTES`: the clocks of the app and of cron differ by seconds); a good `db_dump` or `photo_copy` row further ahead is red by itself, `backup_clock_ahead`, with the figure `clock_ahead = { last_at, hours }` (the newest such row and how far ahead it is; null when there is none), and it does not count for the folder figure, the folder signal or the photo checks either. Before this, one run written by a wrong clock gave a negative age ("-960 hours"), which is never stale, and a dead export looked fresh until the future arrived. The reason lasts as long as the row is in the future; to clear it earlier, correct that row's `ran_at` by hand (S6). `check_runs` is not covered.
- **The folder signal (RV3a-F3, B2, I12)**: `folder_probe = { ok, code, where, at }` is the NEWEST `backup_runs` row of kind `db_dump` that has `$.folder_probe` (the rows the dump and the start-up check write when the probe of the folder fails, and the heal row when it passes again), `null` when there never was one; `ok` false is read from `JSON_VALUE` as the text `0` or `false` (MariaDB 11.8 gives `0`). The red reason `backup_folder_unusable` (after `backup_files_fell`) holds while that newest probe says `ok` false and no `ok` = 1 row of `db_dump` or `photo_copy` is newer than it. It is also one of the reasons that make `GET /internal/jobs/health` answer 503 (with `dump_never`, `dump_stale` and `download_red`), so the GitHub workflow fails the first hour after the folder was lost and not 26 hours later.
- **The photo copies (RV3a-F1, B2)**: `photo_files = { repaired, repaired_at, damaged, damaged_at }` from `backup_runs.detail.verify` of the `photo_copy` rows (written by the nightly check of the copies, `src/jobs/photoVerify.ts`, below). `repaired` = copies that had vanished from the folder and were written again in the last 7 days (amber `backup_photos_repaired`); `damaged` = copies found with another size or other bytes (never overwritten) that the newest row with a `verify` still names (red `backup_photos_damaged` until a newer row names none, which needs the damaged file to be removed by hand).
- Size (P5): `DATA_LENGTH + INDEX_LENGTH` of every table except `design_photos`, after an `ANALYZE TABLE` of each, plus `SUM(byte_size)` of the live photos, plus 12 percent. `information_schema` alone lags badly for a few large rows (65 MB of photos read as 0.0 MB). `analyze: false` skips the ANALYZE when the API caches the answer.
- Red also when the last check says Problem, a check, export or photo copy is older than 26 hours **or never run**, or the size is above 2 GiB. "Never run" is red on purpose: a new shop is not backed up until the first tick has run. `rights.extra` lists any other box of A3 that is on although it should be off (the start-up check notes it in the log, T-F08).

## Where the copies go (Harsh's decision of 15 Oct: no Cloudflare R2)

The export files and the once-only photo copies go to a backup folder on the Hostinger plan instead of an R2 bucket; same layout, same encryption, same create-once rule. What is given up (per the API-design session): the off-site copy and the bucket locks, so a compromised app could delete backup files; Hostinger's own daily backup and the delete triggers are the only other protection, the plan expires on 22 March 2027, and the only copies outside the account are the owner's monthly download and Harsh's weekly pull. The restore tool on the Mac must fetch the folder (SFTP/SSH, never tried) and hand `restoreDatabase` a `Source` (`directoryStore(unpackedFolder).source`) and a `PhotoStore` (`directoryPhotos(pulledPhotosFolder)`).

## The dump job (API34; spec B2, I8 (B), D17, D25)

`node scripts/job.js dump` is started every hour by a Custom cron job whose command is the one hPanel generated for the Node.js type (the app's Node 24 binary, `--env-file` of the deployment's environment, the script of the current build) with `dump` at the end. Its settings are the environment only: `DB_HOST DB_PORT DB_NAME DB_USER DB_PASSWORD JV_BACKUP_DIR BACKUP_PUBLIC_KEY` (`loadPublicKey` reads the key; it is the output of `npm run keygen`). **The Custom command field takes at most 255 characters** and hPanel's command is 161 plus twice the site folder name plus `dump`, so it does not fit for a site folder name of about 45 characters or more: then put the command in a small shell script in the home folder and make the cron command `sh /home/<user>/jv-dump.sh`, or add `--load-env=<the deployment's .env file>` to the script's own arguments (a variable that is already set wins; the flag is not `--env-file` because Node looks for that one itself, anywhere on the command line). Never add `> /dev/null 2>&1`: the output and the exit code are how a failure is seen. Exit code 0 = done, not due, already done or another dump in charge; 1 = the folder cannot be used or the dump failed (recorded); 2 = wrong command or a missing setting.

One run, in this order (`runDumpJob` in `scripts/dump-job.mjs`):

1. **One connection of its own**, opened through the pacer (and once again after 1.1 s if the server refuses it with `EPERM`), with the settings of S11 and `wait_timeout` 300 and `max_statement_time` 20 (I8). Nothing is pooled and nothing is kept.
2. **The folder is tested on every run**, also one that would end as "not due" or "already done": `probeBackupSetting(JV_BACKUP_DIR)`. A folder that is missing (`ENOENT`), not a folder (`ENOTDIR`), read-only (`EACCES`, `EROFS`) or full is never read as "nothing due": the run ends with exit 1 and nothing is dumped.
3. **What is due**: before 02:00 in Asia/Kolkata nothing; nothing when today's `db_dump` row in `sys_job_runs` is `ok`.
4. **The lock** `jv_dump:<database>` (`withJobLock`), released in a `finally`; a dump that finds it taken ends at once. The day's row in `sys_job_runs` (`job` = `db_dump`) is claimed: a `failed` row goes back to `running`, a `running` row older than **30 minutes** is abandoned and taken over, a younger one is left alone, `ok` ends the date.
5. **The export**: `writeDailyExport` with `exportDatabase` as one snapshot (`record` writes the pending row `backup_runs` ok = 0 with `detail.export = { name, sha256, size }` BEFORE the link; on a retry `readRecordedExport` hands the record back, so a crash between the linking and the `ok` row is repaired by writing the `ok` row, and a final file that differs from the record is left alone and this run writes `daily/<date>-<run id>.enc`).
6. **The `ok` row**: `backup_runs` kind `db_dump`, `ok` = 1, `bytes` = the file size, `detail` = `{ phase, run_id, status, export: { name, sha256, size }, counts (rows per table, as the manifest), monthly, folder: { files, bytes, free_bytes, budget_bytes, daily, monthly, photos } }`. **`free_bytes` is the budget of 50 GB less what the folder holds, not `statfs`**: on the proof `statfs` showed the whole server's volume (9.9 TB free), no figure for the plan. The change of the budget is one constant (`BACKUP_FOLDER_BUDGET_BYTES`).
7. **Pruning** (`prune`, after the `ok` row; `readPruneState` is read before it): refused without a good write tonight and with fewer files than the last recorded count (an alert `JV_BACKUP_ALERT`, `detail.prune_refused`), a first real prune only after a logged dry run (`detail.prune_dry_run = { names }`), the newest 30 daily and 13 monthly files always kept. The row's `detail.folder` is rewritten after a prune and `detail.pruned` says how many, so the dashboard does not read the removal as a loss.

A failure writes a `backup_runs` row with `ok` = 0 (`detail.phase` = `failed`, `detail.error`), sets the day's row `failed` and writes `sys_error_log` (`JV_BACKUP_FAILED`); the next hourly run tries again. The alerts of `writeDailyExport` (`export_name_taken`, `export_record_mismatch`) and of pruning go to `sys_error_log` as `JV_BACKUP_ALERT` with `logError`.

**The folder signal (spec 5.2.2, I12).** A failed probe is a `backup_runs` row of kind `db_dump`, `ok` = 0, `detail = { phase: 'folder_probe', folder_probe: { ok: false, code, where } }` (`code` ENOENT, EACCES, ENOTDIR, ..., or CONFIG for a `JV_BACKUP_DIR` that is no usable path; `where` is `folder`, a sub-folder or `JV_BACKUP_DIR`) and a `sys_error_log` row `JV_BACKUP_FOLDER`. The same failure is written again after 24 hours, not every hour. A probe that passes while the newest such row is a failure writes the heal row (`folder_probe.ok` = true). The start-up check of the API (`checkBackupFolderAtStart`, `src/jobs/backupFolder.ts`) writes the same rows and never stops the start. `readHealth` reads this signal (RV3a-F3, above): the red reason `backup_folder_unusable` and the figure `folder_probe = { ok, code, where, at }`.

The photo copy is **not** in this script: it works in the slices of the hourly tick (API33b) with `copyPhotosOnce` over `directoryPhotos(JV_BACKUP_DIR/photos)`.

**The nightly check of the photo copies (RV3a-F1; `src/jobs/photoVerify.ts`, inside the `photo_copy` phase).** Once the photos still to copy are done, the same phase looks at EVERY copy recorded in `sys_photo_copies`: the file exists and has the recorded size (one `stat` each), and a rolling sample is read and compared with the recorded sha256 (at least 20 copies, and `ceil(copies / 27)`, a night, never more than 128 MiB a night, from where last night's sample ended; the cursor `next` is in `backup_runs.detail.verify`, so every copy is hashed within about 28 nights). A **missing** copy (one file, or the whole `photos/` folder when its parent is usable) is written again from the database's bytes after those were compared with the sha256 and size recorded for the copy, through the same temp-file-then-`link()` path as any copy; `sys_photo_copies` is not touched (its rows are only ever inserted); a copy whose photo was removed since (a tombstone, the bytes are gone) is counted as `gone` and is no alarm. A copy that exists with **another size or other bytes** is never overwritten (B2): the phase does everything else, then fails (the tick answers 500, one `ok` = 0 row per night, and one more whenever the set of damaged copies changes), `detail.verify.damaged` names up to 50 of them, and the next nights hash every copy named there whether or not the sample reaches it, until the file is removed by hand and written again. The count of the night (`checked`, `missing`, `repaired`, `repaired_bytes`, `gone`, `hashed`, `hashed_bytes`, `damaged_total`) is in the job's `detail.verify` and in the `ok` row of `backup_runs`. The check shares the slice's 25 seconds: when it runs out the row stays `running` with `detail.verify_state` and the next tick goes on. If the dump cannot write the folder (O48), the same `exportDatabase` runs from the Mac through Remote MySQL (O49), paced, with a directory sink.
