## 1. Design: the simplest approach that meets the spec

- **Backend first, and most of its database half exists.** The order Harsh asked for ("pehle Backend") stays. What is built and green in `jewelvault-api` (521 tests on 15 Oct 2026, 630 on 16 Oct, and 567 in `tests/schema` alone since commit `694b435` on 17 Oct): the schema, the create-only migration runner, the four derived reads as query files, the invariant SQL, the health query, export, photo copy, restore, the import and the rebalance library (section 2). The Node API (`src/`) does not exist yet: it is tasks `API01` to `API36`.
- **Money rules run in Node, on the same `pricing.ts` file the screen uses** (a byte-identical copy with a hash check, spec C12), inside one transaction per service function, with one lock order (customer, then pieces by one `ORDER BY id FOR UPDATE` statement, then the number counter last), repeat-safety by the `Idempotency-Key` claim, and no `DELETE` anywhere (spec S7).
- **Two repositories.** `jewelvault-api` (private on GitHub once Harsh pushes it; deployed to Hostinger by its GitHub app) holds the database half and the API. `jewelvault-app` (Vercel) holds the static site; its Supabase pieces (`authStore.ts`, `supabase/client.ts`, the Supabase lane scripts and migrations) are replaced by an API client and removed in `WEB15`, together with preview mode. The stores keep their exported names, so about 15 files that write data change, not all 37 (spec section 5).
- **Test tools.** Vitest on a throw-away MariaDB 11.8 in Docker with its data in tmpfs (no volume, removed with `docker rm -fv` of its own name; the guard container `keep-tourstack-and-unknown-volumes` is never touched), Fastify `inject()` for HTTP tests, Playwright for the browser, small scripts for BUILD checks, written logs for DRILLs. **Every test is written first and seen failing for the right reason** (Playbook 3.3); each spec test is a `describe('T-xxx ...')` block, so `npm test -- -t T-C09` finds it. The database server is set to Hostinger's non-strict `sql_mode` and READ-COMMITTED so the tests prove the API's own per-connection settings, and the application user is the ten-box user of spec A3.
- **Next.js 16 is not the Next.js the agents know.** `jewelvault-app/AGENTS.md` says its APIs and file structure may differ from training data: every front-end agent reads the relevant guide in `node_modules/next/dist/docs/` before writing code, and heeds the deprecation notices (the site is a static export: no server code, no rewrites or headers in `next.config`; headers go in `vercel.json`, spec H1).
- **One lane, one database.** Each agent has its own MariaDB container (`jv-mariadb-<lane>`, port 33310 plus the lane number: main, a, b, c) from `npm run db:lane`, because two agents on one database would reset each other's data. The application opens one pool of 8; tests and tools pace themselves to 10 new connections in 1.2 seconds (Hostinger refuses the 21st new connection inside about a second).
- **Three agents at most at once** (Playbook 1): **A** the money core, **B** the front end, **C** the rest of the API, side tasks and the reviews. The **orchestrator** (the main session) is not an agent: it merges locally, runs the tasks that need Harsh at hPanel (lane O), keeps the ledger and tells Harsh in short Hinglish. Each agent works in its own `git worktree` on its own branch (`api-a`, `api-b` and `api-c` of `jewelvault-api` in `jewelvault-api-wt/a`, `b`, `c`; `api-web` of `jewelvault-app` in `jewelvault-app-wt/b` for agent B and `api-web-c` in `jewelvault-app-wt/c` for the one front-end task of agent C, `WEB14`); the front-end tests start the API from the orchestrator's checkout of `main` of `jewelvault-api` (`JV_API_DIR`), into which the orchestrator merges each finished API task before the web task that needs it starts; the old Supabase worktrees (`jewelvault-wt/a`, `b`, `c`) are not used. One local commit per task: what changed, the spec IDs it covers. **Nothing is pushed or pulled by any agent; Harsh pushes** (his GitHub account `iamharshvishwas`), and after each commit the orchestrator says which branch and commit are ready.
- **One owner per function.** A service function X1 to X12 is edited only by the task that first creates it, with its final signature from its first commit; what a later task adds, it adds in a helper that the function already calls (`rebalance`, `cashRules`, `state`, `touch`), so two agents never edit one function. A bug found in another task's function goes to the orchestrator.
- **Migrations** stay forward-only and create-only (spec S9). Until the first one is applied to a real Hostinger database (`OPS03`), a migration file may still be edited by the database session's alignment work (`MB07`); after that, every change is a new file and the runner refuses edits. `db/` is changed only through the tasks that name a migration.
- **Hostinger rules the code follows** (measured on Harsh's plan on 15 and 16 Oct 2026, `HOSTINGER-SPIKE.md`): no request over about 50 seconds (a 60-second cut gives a 504); one pool of 8 and at most 20 new database connections a second; every connection sets `wait_timeout` 300; only Custom-type cron jobs (the Node.js type cannot be listed or deleted); nothing durable in the build folder; every deploy starts the app twice about 10 seconds apart; `x-real-ip` is the visitor's address; the app reaches the database at `127.0.0.1`.

## 3. Tests

The spec defines 123 tests (section 15). A test is **introduced** in the one task where everything it exercises exists (the generator checks this against the dependency graph, with a printed list of every name in a test's Req column that is deliberately finished by a later task: appendix); a task that **extends** a test writes a part of it (a clause of the test, named in the appendix with its owner). Catalogue-based tests (T-D01, T-D02, T-D09, T-D10, T-D11) are written once and cover every route or function added after them. The plan adds named plan tests (`PT-...`) where the spec has none. **Suites:** `npm test` (everything in `jewelvault-api`, about 1 to 2 minutes now, more later), `npm run test:http` style subsets by `-t`, `npm run check:static` and `check:pricing`, `npm run verify` (typecheck, build, checks, all tests); in `jewelvault-app` `npm test` (unit), `E2E=1 npm run verify` (Playwright against a lane); DRILL logs in `docs/drills/`. A task is done only when every suite that existed before it is still green.

## 5. Honest estimates

**What was measured.** On the Supabase build (`Completion-Plan/_build/p1-plan/unit-samples.csv`) 11 tasks took 417 agent minutes for 10.9 plan-days: about **38 minutes a plan-day** (a working day of 8 hours is 480 minutes, so 0.08 of a day), all of them pure database or pure TypeScript tasks with a written oracle, plus 20 to 25 minutes of the orchestrator's own check on some; the first five database tasks (5.3 plan-days) took 4.1 hours. The new database half ran faster still (steps 1 to 3 and the three remaining jobs in about one working day each). **What was never measured:** a money write function, a two-session concurrency test, a Hostinger deploy through GitHub, an import, anything that waits for a person. A browser task was measured once (`FE02` of the old build: login, session gate, roles and browser tests, 1.4 plan-days in 30 agent minutes), but with the back end mocked.

**So each task has a speed group with a low and a high factor** (elapsed working days of the chain per plan-day, `_plan-build/plan_core.py`), and the plan reports every date as *best*, *likely* (the average) and *worst*:

## 11. Deploy, rollback, nightly checks, backups and drills

- **Deploy (staging, then production):** Harsh pushes the `staging` (later `main`) branch of the private repository from GitHub Desktop; Hostinger's GitHub app builds it (`tsc` on its side, entry `dist/server.js`). Environment variables are typed by Harsh in hPanel, never in chat; changing one redeploys. **Every deploy starts the app twice about 10 seconds apart, so nothing is tested for 30 seconds afterwards; production deploys and variable changes happen only when the shop is closed.** `OPS03` writes `DEPLOY.md` with the exact clicks and times.
- **Rollback:** the API by a revert commit pushed and redeployed (`OPS03` tries it once on purpose); the website by promoting the previous Vercel deployment; a bad migration is fixed forward with a new file (the runner refuses edits), and a damaged database is restored into a NEW empty database (the application user has no Drop), keeping the old one until the owner agrees (spec B5, `RUNBOOK.md`).
- **Nightly checks:** the hourly tick (`curl` from a Custom cron job, plus a scheduled GitHub Actions call as the second caller) runs the nightly check after 02:00 Asia/Kolkata once a day, writes `check_runs`, closes login-failure hours, empties old idempotency results and copies photos; the dump is a separate Node script from a second Custom cron job (one snapshot, never sliced). The owner's dashboard line turns red after 26 hours; the failing workflow e-mails the repository owner; Harsh reads the check each morning for the first two weeks (`QA06`), and for three nights on staging before go-live (`OPS08`).
- **Backups:** nightly encrypted export and once-only photo copies in the backup folder on the plan (`JV_BACKUP_DIR`), Hostinger's own daily backup, Harsh's weekly pull to his Mac (O54) and the owner's monthly Download everything: the only copies outside the account. Siddhi is told in plain words that up to 35 days of entries and all photos could be lost with the account (`PS06`).
- **Drills:** drill 1 into Docker on the Mac (`OPS05`), drill 2 into a second Hostinger database through Remote MySQL (`OPS07`), drill 3 seven days after go-live (`QA06`); the balance rebuild from the zip, the weekly pull and the three admin commands once each (`OPS05`); the runbook is accepted when someone who did not write it restores the throw-away copy (`OPS06`).
