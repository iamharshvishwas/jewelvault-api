# JewelVault database schema, draft 1 (step 3), MariaDB 11.8

Date: Thursday 15 October 2026. Draft, not reviewed by a second agent yet. It follows spec section 2 (Part A data model, D1 to D23) as changed by the move to Node.js + MariaDB, `NODE-DESIGN.md` (Appendix A and questions D-Q1 to D-Q10), `PART-A-MARIADB-MAPPING.md`, `HOSTINGER-FACTS.md` and Harsh's decisions of 15 Oct (photos inside MariaDB, at most 3 per design, 1000 px longest side, JPEG quality 72).

**Nothing here was run on Hostinger.** Everything was run on a local MariaDB 11.8.9 with Hostinger's isolation level. Applying it to the real database is a separate, small step (section 6).

## 3. How this differs from spec section 2 (for the amended spec)

| Spec | Here | Why |
|---|---|---|
| D1 `profiles` on `auth.users` | `users` (e-mail, name, role, active, password hash, must_change_password) and `sessions` (token hash, expiry, revoked) | Supabase Auth is gone (NODE-DESIGN 2.3) |
| S1 `public` / `private` schemas | one database; internal tables are named `sys_...` | no exposed schema exists any more |
| D3 `settings.key` | `settings.setting_key` | `key` is a reserved word in MariaDB |
| D6 `tags text[]`, `image_paths text[]`, `primary_image_path` | `tags` JSON array; `photo_ids` JSON array (at most 3, CHECK) and `primary_photo_id`; new table `design_photos` | photos live in MariaDB (Harsh); MariaDB has no arrays |
| P1 to P4 storage bucket | `design_photos` (`id` + `kind` full/thumb as key, mime jpeg/png/webp, `byte_size` 1 to 2 MiB equal to the stored bytes, sha256, `MEDIUMBLOB`) | same |
| D7 weight rules (net not above gross; net above 0 for By Weight) | **not in the database**: API rule (O37 says it runs only on insert and on a weight change, never on a status change; the second needs the design) | a CHECK runs on every update and would block a status change on an imported row |
| D7 "selling_method cannot change while pieces exist", D5/A5 archive rules | API rules | need other tables |
| D10 partial unique index (one walk-in) | generated column `walkin_key` + UNIQUE | MariaDB has no partial index (tested) |
| D10 PAN rule | `BINARY pan REGEXP ...` | a plain REGEXP is case-insensitive here (tested, a lower-case PAN slipped through) |
| D10 mobile | CHECK: ten digits or `+` and 7 to 15 digits; blank only with an import batch or for the walk-in | O33 |
| D11 `bills.request_id uuid unique` | nullable UNIQUE (imports have none) | |
| D11, R8 | extra CHECKs: estimate totals are whole rupees; `round_off` within ±0.50; cancel reason, time and person all present exactly when cancelled | the database re-checks what R8 and D11 promise |
| D12, R6, R7 | extra CHECKs: By Weight line has quantity 1; `item_total = metal + labour + piroi + other charges` to the paisa | proved against `pricing.ts` by the workload test (about 1,600 committed operations over 3 random runs, none refused by a CHECK) |
| D13 `kind` ties | one CHECK ties kind to mode, amount, grams and rate; no `Credit` mode; opening advance only as money with mode Other or as silver | the first draft let a money receipt with no mode through (a CHECK that evaluates to NULL passes); found by the tests, fixed with `IS NOT NULL` |
| D14 composite foreign keys | as specified (`receipts(id, customer_id)`, `bills(id, customer_id)`) | |
| D16 `audit_log` | + `request_id`; written by Node in the same transaction (default of D-Q2) | no `row_to_json` in MariaDB, and triggers are not proved on Hostinger |
| D17 `backup_runs.kind` | `db_dump`, `restore_drill` (no `photo_copy`) | photos are in the dump |
| D18 `private.counters`, `idempotency`, `limits`, `import_batches` | `sys_counters`, `sys_idempotency` (+ `claim_token`, `result` JSON), `sys_import_batches`; `limits` is `db/limits.json` plus CHECK literals | |
| D19 indexes | as specified; every foreign key has an index (MariaDB makes one); every polled table has an index starting with `updated_at` | |
| D22 forced person columns, D23 touch triggers | no triggers: the API sets person columns from the session and does the touches in the transaction (D-Q2, D-Q3); `updated_at` has `DEFAULT` and `ON UPDATE CURRENT_TIMESTAMP(6)` as a backstop | |
| "one live line per piece" | **not a constraint**: invariant I2 plus the piece row lock (K2) | a UNIQUE key on a flipping generated column deadlocked with the counter (spike F2) |

Added tables: `users`, `sessions`, `sys_login_attempts`, `sys_job_runs`, `sys_error_log`, `design_photos`.

## 5. Rules that stay in the API (not in the database)

Net weight versus gross weight and By Weight net above 0 (O37); `selling_method` lock while pieces exist; role of every caller and which fields each role may read or write (the route matrix); "a user cannot change their own role or active" (A8); the biller's date limits (Y8, D4); the cash limit and PAN prompt (Z1 to Z3); photo count per design counted from `design_photos`; image type from the first bytes; decimals beyond the column's scale (MariaDB rounds `1.239` silently); "more than 3 photos" is also a CHECK on the id list.

## 6. Applying it to Hostinger (Harsh's steps, when the API-00 proof is done; not done)

1. In hPanel create the JewelVault database and user (Databases, Management). Create nothing else.
2. Run the schema: either `DB_HOST=... DB_USER=... DB_NAME=... DB_PASSWORD=... npm run db:migrate` (password only from the environment) after allowing his IP in Remote MySQL, or paste `db/schema.sql` and `db/seed.sql` in phpMyAdmin's SQL tab.
3. Try the optional trigger file (`npm run db:migrate -- --optional`); if it fails with a privilege error, leave it out.
4. In hPanel, Change Permissions for that user: untick **Delete** and **Drop** (keep Alter, Create, Index, References, Trigger so later migrations still work).
5. Run `tests/schema` against it only on a throw-away copy (the suite creates databases; it must never run on the real one).
