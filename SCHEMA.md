# JewelVault database schema, draft 1 (step 3), MariaDB 11.8

Date: Friday 16 October 2026 (aligned with spec **draft 5.2**; first written on 15 October for draft 5). Draft, not reviewed by a second agent yet. It follows spec section 2 (Part A data model, D1 to D26) as changed by the move to Node.js + MariaDB, `NODE-DESIGN.md` (Appendix A and questions D-Q1 to D-Q10), `PART-A-MARIADB-MAPPING.md`, `HOSTINGER-FACTS.md` and Harsh's decisions of 15 Oct (photos inside MariaDB, at most 3 per design, 1000 px longest side, JPEG quality 72).

**Nothing here was run on Hostinger.** Everything was run on a local MariaDB 11.8.9 with Hostinger's isolation level. Applying it to the real database is a separate, small step (section 6).

## 4b. Choices made in the reads and invariants (read before reviewing them)

- A **live allocation** is `released_at IS NULL` AND the receipt is `active`. A voided receipt's allocation is never counted, released or not (V1, V2, I3).
- **Dates are Indian, and stored.** A cancel is dated `bills.cancelled_on` and a void `receipts.voided_on` (DATE columns, present exactly when cancelled or voided, from the API's Asia/Kolkata clock, D11, D13): no query converts a UTC time. Stored times are UTC.
- **I3 is read literally**: any allocation that is not released and points to a cancelled bill fires, also one that belongs to a voided receipt. So `cancel_bill` must release EVERY open allocation of the bill, not only the live ones (K3 says "the bill's allocations"). If Node would rather leave a voided receipt's allocation alone, say so and I3(c) gets `AND r.status = 'active'`.
- **I5** parses the series from the number (`<prefix>-<YYYY>-<digits>` gives `bill:<prefix>:<YYYY>`, `OB-<digits>` gives `opening`), ignores bills with an `import_batch_id` and numbers at or below the counter's `seed_value`, and also requires the counter's `last_value` to equal the highest issued number. A number in neither format that a function issued is reported.
- **I6 (SQL half)** takes `subtotal` as the sum of the lines' `item_total` and `grand_total` as `ROUND(subtotal - discount + additional_charges, 0)` exactly as spec 12 says (GST is not in this sum). If GST is meant to be added, the spec line and this file change together.
- **I7** lists every DECIMAL column of the business tables by hand; a test fails if a new DECIMAL column is added without being listed (round_off is the one exception).
- The runner leaves the caller's isolation level alone and must not be called inside an open transaction (`START TRANSACTION` would commit it).

## 4c. Things found while writing the import, the export and the restore

- `sys_counters.series` is now `VARCHAR(100)` (it was 60): the series `sku:<design_no>` with a 64-character design number needs 68.
- `designs.photo_ids` refuses a value that starts with `data:` (spec P4, I7).
- **UUID order is not text order.** MariaDB's `UUID` type sorts by its own order. Keyset paging that compares ids as text, or that aliases a column to its own name (`CAST(id AS CHAR) AS id ... ORDER BY id` sorts the text), skips and repeats rows. The export hit this with random v4 ids; the API's polling (C4) must not.
- **Plan trap after a bulk load.** With stale statistics MariaDB re-built a grouped derived table once per customer (`LATERAL DERIVED`, the `split_materialized` switch): I10 on 30,000 bills took more than 500 seconds, against 0.1 second with the switch off. `runInvariants()` switches it off for its own snapshot and puts it back; the restore and the import run `ANALYZE TABLE`. Any report that joins a view to `customers` over thousands of rows should be checked with `EXPLAIN` for `LATERAL DERIVED`.
- The rebalance (Y6) lives in `scripts/rebalance.mjs` so that the import (IM4) and the API (X12) use one copy. The API session can import it or port it; the tests in `s14` define what it must do.

## 4e. Changes of spec drafts 5.1 and 5.2 (what moved in the database, 16 Oct)

- **S9 re-runnability:** every statement of a migration or trigger file is in its `IF [NOT] EXISTS` form (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, ...), seeds are `INSERT IGNORE` or `ON DUPLICATE KEY UPDATE`, trigger files are `DROP TRIGGER IF EXISTS` + `CREATE TRIGGER IF NOT EXISTS`; the runner checks all of it before anything runs, and a test applies every file twice.
- **V1 and the state reads are correlated sub-selects (RM5-1, RM5-2):** never a join to a grouped derived table (a plan trap on prepared pooled connections, error 1969), `FORCE INDEX` on the allocation indexes so that stale statistics cannot send a sub-select into a scan. `S1` to `S4` read what is open **at call time, after the change**, so what a void, a cancel or a re-issue re-opened is in it; `rebalance.mjs` reads S1, S2 and the one-customer V2. T-F11 (`s17`) builds a 10,000-bill customer, reproduces the failure of the join form as a negative control and proves the correlated form inside the statement limit.
- **`sys_error_log` cap (D25, RF5-16):** `minute_at` and `seq` (1 to 20) with `UNIQUE (code, minute_at, seq)`; `logError` takes the next free place in the same statement and beyond 20 adds one to `detail.suppressed` of the row with seq 20.
- **Photo caps (P2, O56):** `insertPhotoGuarded` inserts in ONE statement that refuses a fourth photo on a design and an unattached photo beyond 60 photos or 100 MB; `unattachedPhotos` is the figure for the screen.
- **Admin door (U3):** `clearLoginCounters` (n = 0 and the window to now on every row of the scopes `email`, `addr`, `any`; the summary row stays) and `recordPull` (`settings.last_pulled = { at, by, file, sha256 }`).
- **Login counters (D24, T-D30 database half):** `scripts/login-counters.mjs`. 44,000 failed logins (20,000 invented e-mails and 2,000 for one e-mail over 50 addresses, twice) leave 1,124 rows in `sys_login_attempts` (limit 2,050) and one summary event; 24 hours of continuous attack write 24 `login_failures` events and none per attempt. The claim of the hour is a compare-and-swap on the window AND the count (exactly one caller wins, no failure is lost), not the bare `WHERE window_start < ?` of the spec text, because the winner must learn the count it closes.
- **Health (I12):** the owner's download, Harsh's pull and the folder's file count; see `BACKUP-RESTORE.md`.
- **Backup folder (B2):** the export is written as one encrypted file with `.partial`, `fsync` and `link()`; the retry rule, the monthly link and the pruning guard rails are in `scripts/backup-folder.mjs`; `backup_runs.detail` carries `folder`, `pruned`, `prune_dry_run` and `export`. No migration: they are keys of an existing JSON column.
- **Audit triggers (L1 (a)):** `db/optional/0910_audit_triggers.sql` is **generated**. The transaction wrapper sets `@jv_actor`, `@jv_role` and `@jv_request` at the start of each transaction and clears them at the end (the variables live on the pooled connection and survive a commit); with none set the row has no actor and the role `sql` (a change typed by hand in phpMyAdmin), the import sets the role `import`, a job `job`, the admin door `admin-cli`. A malformed actor stops the change (error 1292): nothing is changed unaudited. **Never both:** a database with these triggers must not also have the API write the same rows, and `runImport` with `audit: 'auto'` (the default) uses the triggers when they exist and refuses the other settings. Money and BIGINT are text in the row, JSON columns are JSON. Tested on 11.8.9 (`s20`, 16 tests, also as the ten-box user and applied twice) and under load: the lock-order workload of `s8` (8 workers x 3 seeds, no retry) runs with the triggers installed with 0 deadlocks and 0 lock timeouts, writes about 12,000 update and 12,400 insert audit rows, and afterwards every inserted row has exactly one insert audit row and the last audit row of each piece, bill and allocation equals the row; **not yet on the plan**: the proof kit has a step for it.

## 5. Rules that stay in the API (not in the database)

Net weight versus gross weight and By Weight net above 0 (O37); `selling_method` lock while pieces exist; role of every caller and which fields each role may read or write (the route matrix); "a user cannot change their own role or active" (A8); the biller's date limits (Y8, D4); the cash limit and PAN prompt (Z1 to Z3); photo count per design counted from `design_photos`; setting the three session variables of the audit triggers at the start of each transaction and clearing them at the end; image type from the first bytes; decimals beyond the column's scale (MariaDB rounds `1.239` silently); "more than 3 photos" is also a CHECK on the id list.

## 6. Applying it to Hostinger (Harsh's steps, when the API-00 proof is done; not done)

1. In hPanel create the JewelVault database and user (Databases, Management). Create nothing else.
2. Run the schema: either `DB_HOST=... DB_USER=... DB_NAME=... DB_PASSWORD=... npm run db:migrate` (password only from the environment) after allowing his IP in Remote MySQL, or paste `db/schema.sql` and `db/seed.sql` in phpMyAdmin's SQL tab.
3. Try the optional trigger files (`npm run db:migrate -- --optional`: the append-only triggers of `audit_log` and the audit triggers `0910`); if it fails with a privilege error, leave them out and the API writes the audit rows instead (never both, L1). Apply them when the shop is closed: re-applying replaces the triggers one by one.

5. Run `tests/schema` against it only on a throw-away copy (the suite creates databases; it must never run on the real one).
