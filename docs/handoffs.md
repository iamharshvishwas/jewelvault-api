One heading per task; the next task reads the lines of the tasks it depends on.

## API01 Repo skeleton, lane harness, config, logging, clock
- Pick a lane for your checkout: `echo a > .lane` (untracked) or `JV_LANE=a`, then `npm run db:lane -- up a`. `npm test` then points at that lane; with no lane it still uses the old spike container on 33307. A chosen lane that is not up stops the run.

The server's global `sql_mode` is Hostinger's non-strict one: API02 must set strict per connection.
- `buildApp({ config, clock?, logStream? })` returns an unstarted Fastify app with `app.config` and `app.clock`; tests pass `testConfig()` and `logSink()` from tests/api/support.ts. A clock reading `{ micros, timestamp, date }` is one instant: take `voided_at` and `voided_on` from the same reading. Fake clocks: `createClock(() => micros)`.
- `src/config.ts` lists the variables (`CONFIG_VARIABLES`); add yours there and to `.env.example` (a test checks both). `src/logging.ts` holds the redact list.
- Build: `tsconfig.build.json` (NodeNext, rootDir `src`, so src imports end in `.js` and cannot import `scripts/*.mjs`); API02 must decide how the start-up check reaches the migration runner. `tests/api/support.ts#buildDist` compiles into `node_modules/.cache` for tests that spawn the server.

## API02 Connection layer: one pool of 8, per-checkout session settings, paced connect, start-up check
- Take connections only from the pool: `createDbPool(config.db)` (src/db/pool.ts), `const conn = await pool.checkout()` gives a mysql2 promise `PoolConnection` with the seven settings of S11 set (one `SET SESSION`, also the aliveness test). Call `conn.release()` (or `conn.destroy()` for a broken or killed one) on EVERY path; both are idempotent and give the pool's place back. `app.db` is the pool (null in tests built without one), `pool.stats()` is `{size, inUse, waiting, opened}`. The tick's 20 s statement limit is a `SET SESSION` after checkout; the next checkout resets it.
- The places are counted before mysql2 is asked: 8 taken, 16 waiting (FIFO, each with its own 2 s timer), the rest refused at once. Start the 12 s deadline of S12 BEFORE `checkout()`, because the wait is part of it.
- Errors are plain classes (src/db/errors.ts): `DbBusyError` has `code 'JV_BUSY'`, `reason` (`queue_full`, `wait_timeout`, `connect_refused`, `connection_lost`, `closing`) and `nothingStarted: true`; API03 maps it to 503 + `Retry-After`. Everything else comes through untouched (`ECONNREFUSED`, access denied, a SQL error): API03's map must classify it. An EPERM is warned in the log and retried once after 1.1 s; a dead idle connection is replaced twice, the third is `connection_lost`.
- `buildApp({ config, db })` runs `runPreflight(db)` in an `onReady` hook (before `listen()` accepts anything, before the first `inject()`) and keeps the result in `app.startup`; while it is not ok every request except `GET`/`HEAD /healthz` is `503 JV_UNAVAILABLE` with the S8 body `{error:{code,message,details},request_id}` (no `Retry-After`, no `X-Request-Id` yet); the reasons are logged only. Without `db` there is no check and no gate (tests of other tasks, `check:routes`). The Delete/Drop answer is `app.startup.amber` and `.rights`; the dashboard line itself is still `readHealth`.
- The start-up check does not use the migration runner (src cannot import `scripts/*.mjs`; migrations reach the database from Harsh's Mac, O49). The tables the code needs are `REQUIRED_TABLES` in src/db/tables.ts (25, without `schema_migrations`): when a migration adds a table, add it there, a T-F08 test compares the list with db/migrations and a migrated database. `src/db/pacer.ts` is the TypeScript twin of `scripts/pacing.mjs` `createPacer`; the pool opens every new connection through it; a T-F08 test keeps the two equal.
- The isolation check reads the server's own `@@global.transaction_isolation` (what a fresh connection gets, the thing that can "change") and the session after the checkout. Test helpers (tests/helpers.ts): `scratchDatabase(label, {schema})` (own database and ten-box user, `drop()`), `laneRoot()`, `laneDbSettings()`, `paced()` (the harness pacer, 10 per 1.2 s). `/readyz` of NODE-DESIGN 5.2 is not built (not in the task).

## API06 Wire formats: Zod parsers for money and weight strings, limits constants, response formats
- Inputs: `import * as wire from './wire/zod.js'`, then `wire.parseInput(wire.strictObject({ ... }), request.body)`. Building blocks: `wire.amount` (text, at most 2 decimals, at most 1,000,000,000), `wire.rate` (2 decimals, 100,000,000), `wire.weight` (3 decimals, 100,000), `wire.quantity` (JSON integer 1 to 1,000), `wire.billLines(item)` (1 to 200), `wire.uuid` (lower case), `wire.businessDate`, `wire.timestamp`. Use `strictObject` for every object, nested ones too (unknown keys refused). A schema returns the text it was given, unchanged ("1.230" stays); hand it to `parseRupees` / `parseGrams` afterwards. Zero is allowed; "greater than 0" (a payment) and the signed `round_off` are for the function schemas.
- A refusal is `wire.InvalidInputError` (`code` 'JV_INVALID_INPUT', `status` 422, `field` like `items[2].metal_rate`, `details` `{ field }`, a message that never repeats the value). `src/errors.ts` belongs to API03 and did not exist: map this class to the S8 body there (or make it extend the JvError class). `WireFormatError` (format.ts) is a bug in a response value: answer JV_INTERNAL.
- Responses: `src/wire/format.ts`. `formatRow(row, { total: 'money', gross_weight: 'weight', id: 'uuid', updated_at: 'timestamp', bill_date: 'date' })` leaves other columns alone and refuses a JS number in a money or weight column. `formatMoney` / `formatWeight` take DB text and never round (a digit past the scale throws); `formatMoneyFromPaise` / `formatWeightFromMilligrams` take whole units. Stale check (A5): `timestampFromWire(body.updated_at)` is the exact DB text to compare; never go through a Date (it cuts the microseconds).
- `src/limits.ts` (`limits`, frozen) is the only place for caps and thresholds, named in camelCase (`cashLimit`, `panThreshold`, `discountFlagPercent`, `rateFlagPercent`). `db/limits.json` is untouched; the four thresholds live only in `limits.ts` (D18). `tests/api/limits.test.ts` (T-F02 clause) lists every CHECK column that has a cap (`CAP_COLUMNS`): a migration that adds a cap-sized upper bound must add the column to that list or the test names it.
- Left to later tasks: the T-A09 clauses for bills, lines, payments, refunds, opening balances and fine_cash call these building blocks inside their own function schemas (API18, API20, API22, API24, API27, API28). The clock sentence of T-F09 is proved by `tests/api/clock.test.ts` (API01); `tests/api/wire.test.ts` adds the wire-level case.

## API03 Transactions: withTx, deadline, deadlock re-run, error map, statement wrapper, SIGTERM
- Writing calls: `const ctx = txContextFor(app.db, request, { id: userId, role })` then `withTx(ctx, async (tx) => { ... tx.rows(sql, [..]) / tx.run(sql, [..]) ... })` (src/db/tx.ts); reads: `withRead(ctx, (db) => db.rows(...))` (SELECT and WITH only). `request.id` is now a UUID (the audit log's request_id column is one) and `request.arrivedAt` is taken in the first hook: the 12 s deadline counts from there, pool wait included. A job or import passes `{ id: null, role: 'job' }`; `withTx` sets and clears `@jv_actor`, `@jv_role`, `@jv_request` (MB06). Never catch a database error inside `fn`: after a failed statement every later statement is refused, the call is rolled back and answered with the FIRST failure. A deadlock re-runs `fn` (up to 2 more times), so `fn` must be safe to run again and must not keep state outside the transaction. `tx` is dead once the call returns.
- Errors (src/errors.ts): `throw new JvError('JV_OVERPAYMENT', 'plain message', { details })` for a domain error (`JV_STATUS` has all 23 codes; JV_RATE_LIMITED needs `retryAfter`); `BusyError` is JV_BUSY (reason, `outcomeUnknown` after a lost COMMIT); `DbBusyError` and `wire.InvalidInputError` now extend them. `buildApp` installs the one error handler: S8 body, `Retry-After: 1` on JV_BUSY, causes logged with values removed (`describeCause`). The `route()` wrapper, the 404 handler (JV_NOT_FOUND) and the handler timer (API07: map `FST_ERR_HANDLER_TIMEOUT` is already JV_BUSY here) are not built. ECONNREFUSED and access denied are JV_UNAVAILABLE (NODE-DESIGN 4.5), not JV_INTERNAL; 1040/1203 are JV_BUSY.
- Duplicate keys: `BUSINESS_KEYS` (JV_INVALID_INPUT) and `INTERNAL_KEYS` (a bug, JV_INTERNAL) in src/errors.ts list every unique key by name; a test compares them with a migrated database, so a migration that adds a UNIQUE key must add its name to one of them.
- Statements (src/db/stmt.ts): a refusal (`StatementRefusedError`, `rule`) is a bug in the code and answers JV_INTERNAL. Parameters are text, finite numbers, booleans, null or Buffers, one `?` each (an IN list: one per element, no arrays); JSON columns go as `JSON.stringify` text. The T-D07 grep reads src/ and scripts/ with the TypeScript parser: src/ has no hit; scripts/lane.mjs (3) and scripts/audit-triggers.mjs (2) are named in the test; a new SQL string starting with DELETE, TRUNCATE, DROP or ALTER in either fails it.
- Tests for later tasks: tests/api/tx-support.ts has `txWorld()` (scratch database with the real schema AND the audit triggers, two customers, one counter), `toyWrite`/`toyIdempotent` (the shape of a writing function), `spyOn(pool)` (sees and can fail every statement), `leftovers()`, `innodbDeadlocks()`; API14 and API31 can reuse them. mysql2 3.24.6 expands an object into `col = val` only where `?` stands in a SET list (in a WHERE it writes '[object Object]'); `execute()` never expands anything.
- SIGTERM/SIGINT: `installShutdown(app)` (src/shutdown.ts, called by server.ts) closes the listener, waits for running calls up to 10 s, closes the pool and exits 0; after 10 s it exits 1 and MariaDB rolls back what is open. After close begins every response says `Connection: close` (otherwise an idle keep-alive connection held the shutdown for 72 s). tests/api/fixtures/tx-server.mjs is the child process of the T-C18 tests.

## API04 route() wrapper, permission matrix, session lookup, generated cell tests
- Register an endpoint only with `route(app, { action, body?, handler })` (src/permissions/route.ts): the method, address, roles and U11 flag come from the row in `src/permissions/matrix.ts`; the handler gets `{ app, request, reply, auth, body }` (`auth.user.role` is a value read from `users`; return the payload, or send and return `reply`). Order: session (sessions, then users: two SELECTs, no write), must-change gate, matrix row (all in onRequest, before the body is read), then the strict Zod `body` (a route without one takes no body), then the handler. `route(app, { public: name })` is for the public list, `route(app, { token: 'admin'|'job', method, url, verify })` for the two token doors (`verify` is the door's own check and runs alone). A route made any other way (`app.get`, a plugin's) throws at registration; a plugin that must register its own (API07's CORS `OPTIONS`) needs a line in `FRAMEWORK_ROUTES` (empty now). Anything that is not a route answers 404 JV_NOT_FOUND (the S8 body) with no session read (`installPermissions`, called first in `buildApp`; `/healthz` now goes through `route()`). Application routes are registered in `registerRoutes(app)` of the new `src/routes.ts` (buildApp calls it; `buildApp({ routes: false })` is the test seam that leaves them out), and `app.db` is read inside handlers, never at registration: the catalogue app of the generated test has no pool. - The task that builds a route adds nothing to the wrapper: register it with its action and the generated test (`tests/matrix.generated.test.ts`) walks it for nine callers (no cookie, ended, expired, idle, inactive, must-change, staff, biller, owner), plus the READ_COLUMNS of a read (the answer's keys must be on the list) and the WRITE_COLUMNS of an edit (on the list works, on another role's list 403 JV_FORBIDDEN, unknown 422; `edit.shape` says `changes` or `fields`). A row with no route yet is a vitest `todo` and is listed by `npm run check:routes`. All 51 rows and the 5 public places are already in the matrix (oracle typed from the spec in tests/api/permissions-matrix.test.ts: a row added or changed there changes the oracle too); the sync addresses are kebab-case (`/v1/sync/daily-rates`), the READ_COLUMNS keys are table names, and `read:poll` is a row of its own: its handler asks `mayCall(role, 'read:<resource>')` for each resource named and refuses the whole call.
- Service functions check again at their start with `assertMayCall(role, action)` (JV_FORBIDDEN), and ask the three owner-only field rules by name: `mayUseField(role, 'cash_override_reason' | 'original_net_weight' | 'back_dates')`. No file under src/ outside src/permissions/ may hold the strings or object keys owner, biller or staff (T-D10 reads the code with the TypeScript parser; `NAMED` in the test is the empty list of exceptions). Row rules that are not columns are exported from the matrix for API11/12/13: `STAFF_SETTING_KEYS`, `NEVER_WRITTEN_SETTINGS`, `BILLER_DAILY_TOTALS_DAYS`; `HIDDEN_COLUMNS` says why a column is in no list, and a migration that adds a column or a table makes tests/api/permissions-matrix.test.ts name it until the matrix decides.
- Sessions for API05: the cookie is `__Host-jv_session=<ticket>`; `newTicket()` makes 32 random bytes as 43 base64url characters and `sessions.token_hash` holds `hashTicket(ticket)` (SHA-256 of the ticket text). The lookup reads `expires_at` (set it to login + `limits.sessionAbsoluteMs`) and `last_seen_at` against `limits.sessionIdleMs`: JV_SESSION_EXPIRED when past either, JV_UNAUTHENTICATED for no cookie, an unknown or revoked ticket, a user not active. ## API14 Numbers and repeat-safety: counters, formats, Idempotency-Key claim, ids
- Numbers (src/db/numbers.ts): work the series out ONCE from one clock reading: `const s = billNumbers(app.clock.read(), prefix)` (also `openingNumbers`, `designNumbers(categoryPrefix, designPadding)`, `pieceNumbers(designNo, skuPadding)`, `barcodeFor(barcodePrefix, skuNo)`), `await ensureSeries(ctx, s.key)` BEFORE `withTx` (read first, INSERT IGNORE only if missing, on its own checked-out connection inside the error map), and inside the transaction, counter LAST: `nextBillNo(tx, s)` (look-ahead for imported numbers, at most 100 skips, then JV_INVALID_INPUT; gives `{ n, no, skipped }`) or `nextNumber(tx, s)` (designs, pieces); `takeNumber(tx, key)` is the raw step (insertId of the UPDATE; a missing row is JV_INTERNAL). `sku:<design_no>` is made inside X8's own transaction with `ensureSeriesInTx(tx, key)`. The bill prefix must be known BEFORE the transaction (NODE-DESIGN 5.5 step 3 reads settings after the locks: X1 reads `estimate.prefix` first with `withRead`, and should read it again inside and answer JV_BUSY if it changed). `BILL_PREFIX_PATTERN` is the rule the settings validation (API13) should use for `estimate.prefix`; a prefix outside it is a TypeError (JV_INTERNAL) here.
- Claim (src/db/idempotency.ts): the route wrapper (API19) calls `idempotencyKey(request.headers)` BEFORE the transaction (missing or not a UUID: JV_INVALID_INPUT naming the header; a key in capitals is stored in lower case), then `withTx(ctx, (tx) => idempotent(tx, { key, fn, route, pathIds, body }, work))` gives `{ value, replayed }`; `markReplay(reply, replayed)` sets `Idempotent-Replay: true` and the status is the route's own. `claim(tx, req)` and `storeResult(tx, key, result)` are the two halves for API15's helpers. The actor of the claim is `tx.actor.id` (a user, so a job or import cannot claim), `fn` is 1 to 40 characters `[a-z][a-z0-9_]*`, `route` is the name that goes into the hash, and a stored result must be a JSON object or list (money as strings). The hash layout `{actor, body, path, route}` must not change (a retry after a deploy is compared with the old hash). A row whose result was emptied (L6, API33) refuses a repeat of its key with JV_INVALID_INPUT, as the plan says.
- Ids: `newId()` (src/db/ids.ts) is `crypto.randomUUID()`; a test greps every string in src/ for `UUID()`, `UUID_V7()`, `UUID_SHORT()` and `SELECT LAST_INSERT_ID`.
- Facts found while testing: a caught duplicate-key insert on `uq_bills_no` leaves a next-key lock (the gap before the duplicate is blocked, also at READ COMMITTED), the look-ahead read leaves none, and index entries of rows a test deleted linger until the server purges them, so a lock test must use a prefix no earlier test used. mysql2 hands the `result` JSON column back either parsed or as text (claim handles both). The T-C18/T-C19 clauses run the real helpers: `tests/api/idempotency.test.ts` with the child process `tests/api/fixtures/idem-server.mjs`.

## API07 CORS, CSRF layers, security headers, nothing leaks, error log with a cap
- The layers are application hooks installed by `buildApp` (`src/security/index.ts`: helmet, then CORS, then CSRF), so they run before the session lookup of every route API05 and later register. Token doors (`/admin/v1/*`, `/internal/jobs/*`) are exempt from CSRF and get `cors: false`; API09 must still refuse an admin call that carries an `Origin` header. ## API10 Static checks: catalogue, EXPLAIN, dependencies, secrets scan, source checks (T-D11, T-D29)

- The log (tests/api/statement-log.ts): every SELECT, WITH, UPDATE and INSERT ... ## API05 Login, sessions, cookie, me, logout, activity, change-password, password rules
- Routes: `registerAuthRoutes(app)` (src/auth/loginRoutes.ts, called from `registerRoutes`). `me` and the login answer `{user:{id,email,full_name,role,must_change_password}, idle_timeout_s, absolute_expires_at}`; `me` adds `pricing_sha256`, which is `null` until API18 fills `PRICING_SHA256` in loginRoutes.ts. A wrong CURRENT password in change-password is 422 JV_INVALID_INPUT on `current_password`, never 401 (a 401 would log the person out); a new password equal to the current one is refused too. `logout` and `activity` take no body: send none or `{}`, because an empty body with `Content-Type: application/json` is a 422 from Fastify (WEB01 must not do that).
- Passwords (src/auth/password.ts): `passwords.hash/verify/dummyHash/stats` over one process-wide limiter of 2, `checkNewPassword(password, email)` is U9 (API09's random temporary password needs no check). Argon2id when `crypto.argon2` exists (Node 24.7+), else scrypt N=2^17 maxmem 256 MiB; the Argon2id path was run only through a stand-in on this Node 22, its real-primitive tests (RFC 9106 vector, wrapper, round trip) are skipped here: run `npm test -- -t T-D25` on Node 24 once. A stored Argon2id string on a Node without it THROWS (500), it is not "wrong password". A local part under 3 characters does not count in the U9 rule.
- Login order, for API08 to wrap: read the user (short checkout, given back), verify or dummy-verify (no connection held), then one transaction that locks the user row and checks the verified hash is still current, ends the browser's old session, makes the new one and writes the event. The login does not set `users.last_login_at` (it would bump `updated_at` and every screen would re-read `users`).
- Sessions: write side in src/auth/session.ts (`startSession`, `endSession`, `endOtherSessions`, `sessionCookie`); the read side stays in src/permissions/session.ts and now ends an expired session (`revoked_at`) on the call that finds it, checking the lifetime BEFORE `revoked_at` so the cookie keeps getting JV_SESSION_EXPIRED. The wrapper moves `last_seen_at` with `touchSession` (`withAutocommit`, src/db/autocommit.ts) for every call that gets through except paths under `/v1/sync/` and `session:me` (`countsAsActivity`; spec U4 says "every other call", the plan says `me` does not extend: followed the plan).
- `writeEvent(tx, { table, rowId, facts: { event, ... } })` (src/db/events.ts) needs `tx.actor` (a user, or `{ id: null, role: 'admin-cli' | 'job' }`) and refuses a fact key that names a password, ticket, token, cookie, hash or secret. The three events are table `users`, row_id the user's id, `event` login | logout | change_password.
- Test support: `makeWorld` takes `clock`, `addUser` takes `email` and `passwordHash`, `world.restore(caller)` is called by `checkCell` after every cell (a logout would end the fixture's session); the T-D02 stray-statement check allows the one end-mark UPDATE for an expired or idle caller, and permissions-route.test.ts was changed to say so.

## API11 Read side: sync endpoints, combined poll in one snapshot, keyset paging as UUID, seed-volume
- Routes (`registerSyncRoutes(app, { maxRows? })`, src/sync/routes.ts, called from `registerRoutes`): `GET /v1/sync/<resource>?updated_after=&after_key=&limit=` answers `{rows, next, server_time}`; `POST /v1/sync/poll` takes `{limit?, cursors: {<resource>: null | {updated_at, key?}}}` and answers `{results: {<resource>: {rows, next}}, server_time, role}`. Resources are the address segments (`daily-rates`, `sku-private`, `bill-items`, `receipt-allocations`, `bill-summary`, `customer-balances`), taken from the matrix rows; an unknown name in a poll is 422, a role that may not read one is 403 for the whole call before any page is read, unknown query or body keys are 422. `limit` is 1 to `limits.syncPageRows` (1,000): more is 422, a lowered `maxRows` (the T-F03 cap-500 test) clamps. `next` is set when the page was full, so a last page that is exactly full costs one more (empty) call. Cursor `updated_at` must be the exact 6-decimal `...Z` text (WEB04 must write six decimals when it subtracts the 30 s); a cursor without a key reads `updated_at >= ?`.
